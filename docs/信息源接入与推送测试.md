## 二、接入一个新信息源（3 步）

### 1. 在 `TARGETS` 里加一条

打开 `tools/collect_notices.py`，在 `TARGETS` 列表末尾加：

```python

    "site": "植物保护学院 · 通知公告",       # 展示名（会写进每条的 source_site）
    "unit": "zbxy",                          # 单位代号（用于生成 id）

    "base": "https://zbxy.ahau.edu.cn/",     # 拼详情链接用
},
```

> **怎么找列表页？** 打开学院官网 → 点「通知公告」→ 复制地址栏。
> 只要详情链接长得像 `/info/数字/数字.htm`（常见的 CMS 结构），采集器就能解析。
> 若你的源用了别的详情链接格式，见第 5 节「适配非标准页面」。
> 翻页地址规律实测一致：`/index/tzgg.htm` → `/index/tzgg/2.htm`；在 `TARGETS` 条目里加 `"pages": N` 即可翻 N 页。

## 四、推送引擎怎么打分（当前版本）

分数 = **理由权重之和**，再归一到 0-100。**能展示的理由，一定参与了打分**（单一事实源，理由即分数）。

| 理由 | 权重 | 含义 |
|---|---|---|
| `DUE_TODAY` 今天截止 | **40** | 错过就没了，最高优先 |
| `DUE_3` 三天内截止 | 28 | 较急 |
| `MATCH_COLLEGE` 点名你的学院 | 22 | 本院专属，命中率极高 |
| `KW_MATCH` 命中自定关键词 | **20** | 你亲手输入的具体名词（如「正大杯」）；比订阅标签更强——标签是勾选，关键词是主动敲进去的 |
| `MATCH_GRADE` 点名你的年级 | 18 | 只给这一届 |
| `SUBSCRIBED` 你订阅的标签 | 16 | 你自己勾的 |
| `OPPORTUNITY` 可报名的机会 | 14 | 转专业/奖助/竞赛等「能参与」的，比「须知」更值得推 |
| `DUE_7` 一周内截止 | 12 | 要留意 |
| `MATCH_LEVEL` 面向你的身份 | 10 | 本科 / 研究生 |
| `PRIORITY` 原文标高优先 | 10 | 官方措辞提示较急 |
| `NEW` 新收录 | 8 | 推送的价值在「新」 |
| `VERIFIABLE` 可核对原文 | 6 | 带安农官网链接 |
| `FRESH` 新近发布 | 6 | 无截止日期的条目靠这条不至于永远沉底 |
| `READ` 你常看这一类 | +4 | **反馈闭环**：点开过的同类更懂你 |
| `STALE` 看了没点开 | **-12** | **重复抑制**：别让同一条天天顶头条 |

**三条设计原则**：

1. **可解释**：每一条理由都能追溯到「档案哪一项」或「数据哪个字段」，没有黑箱。
2. **越用越准（反馈闭环）**：你点开某类通知 → 同类后续加权（`READ`）；反复展示却不点开 → 自动降权（`STALE`）。全部只在**本地留痕**，不上传。
3. **不埋没**：池子里约一半通知没有截止日期，靠 `FRESH`（14 天内新发布）给它们一条生路，不会永远沉底。

### 想调权重？

改 **同一个表**（两端各一处，必须一致）：

- 小程序：`miniprogram/utils/push.js` 的 `WEIGHT`
- 网页版：`web/zhishi-core.js` 的 `PUSH_WEIGHT`

改完跑 **`python tools/checks/check_parity.py`** —— 它会逐项比对两端权重，
**任何一项对不上就报错**（`【3b】主动推送引擎 权重表 同源`），防止两端漂移。

## 五、适配非标准页面（你的源用别的链接格式）

默认解析器认 `/info/数字/数字.htm` 这种 CMS 详情链接。若你的源不同：
改 `tools/collect_notices.py` 里的 `parse_list()`，把这一行的正则换成你源的实际格式：

```python
# 现在：
if not re.search(r"/info/\d+/\d+\.htm", href):
    continue
# 换成你的，例如 /content/12345：
# if not re.search(r"/content/\d+", href):
#     continue
```

正文抽取器 `parse_detail()` 覆盖了常见容器（`div.content` / `div#content` / `div.article` / `form` 等）；
若你的源正文抽不到，把它的正文容器选择器加进那个列表即可。

## 六、合规红线（接入前先看这条）

- ✅ **只接公网公开页**：学校主动对外发布的通知栏，等同「人工翻官网」的自动化。
- ❌ **不接**：教务系统后台、任何需登录鉴权的页面、任何私域/个人数据。
- 🔁 **友好抓取**：采集器每条之间 `sleep 0.6s`，不冲击对方服务器；请遵守目标站 `robots.txt`。
- 🏷 **如实标注**：采到的标 `real:true` 并附官网链接；采不到原文链接的如实说明；
  演示样例明确标「非真实通知」，绝不假装有出处。

## 八、受众抽取与定点推送（从原文读出"这条是给谁的"）

> 痛点：如果每条通知的受众都写"全体本科生"，那"推送"就退化成"全员广播"——
> **受众读不准，定点就无从谈起**。这一节讲我们怎么从通知原文把"针对对象"读出来。

### 8.1 抽取在哪一层

`tools/inject_digest_into_mp.py` 的 `pick_audience(title, raw)` —— 它在"注入小程序数据"这一步，
从**标题 + 原文**读取这条通知的针对对象，写进 `notices.js` 的 `audience` 字段。

### 8.2 抽取分两步

**第一步：先判"是不是面向学生的可参与事项"。**
纪委会议、巡察动员、值班安排、经费公示、项目评审公示、学科建设新闻、教职工大会……
这些**从来不是给学生办的**，却混在通知池里占着头条。识别为：

```
非学生事项（行政/新闻）
```

→ 推送层给强负权（`NOT_STUDENT = -30`）并**直接剔出推送流**（仍可在搜索/全库里看到）。

**第二步：是学生事项，就从原文读出针对对象，并合成成一句。**
优先级（越具体越靠前）：

| 维度 | 抽取规则 | 例 |
|---|---|---|
| 学院点名 | “XX学院”（排除“各学院”泛指与“XX大学XX学院”外校） | `机械与车辆工程学院` |
| 年级点名 | `20xx级` / `大一~大四` | `2025级、2026级` |
| 班级点名 | `\d{2}XXX-\d+班` | `23车辆工程-3班` |
| 特定人群 | 党员/考研学子/已报名XX/已申请XX/应届毕业生 | `考研学生` |
| 身份层次 | 本科生/研究生/全校学生/在职教职工/全体师生 | `在校本科生` |

命中多个维度会**合成复合受众**，如：

```
机械与车辆工程学院 · 2025级、2026级
```

抽不出具体对象时写 `未点名具体对象`（**不再写"原文未明确说明"**——那句等于放弃定点）。

### 8.3 只重抽受众、不重跑浓缩（安全更新）

已结构化的条目重跑会被跳过。若只想**更新受众**（保留既有 digest）：

```bash
RESAMPLE_AUDIENCE=1 python tools/inject_digest_into_mp.py
```

它只把 `audience` 换成新抽取结果，digestPoints / deadline 等一律不动。

### 8.4 效果（实测 42 条池子）

| 指标 | 改造前 | 改造后 |
|---|---|---|
| `原文未明确说明` | 26 条 | **0 条** |
| 能点出具体对象 | 少数、且高度雷同 | 15 条（含学院/年级/考研/党员） |
| 判为"非学生事项" | 0 条 | 23 条（已剔出推送流） |
| 推送流条数（本科生档案） | 40 条（≈全员） | **9 条（真·与我有关）** |

改完后，小程序首页推送从"几乎人人 40 条"收敛为"真命中的 9 条"——这才是定点推送该有的样子。

### 8.5 改抽取规则注意同源

受众抽取在 `inject_digest_into_mp.py`（注入层）；
而**消费**受众的是 `miniprogram/utils/identity.js`（匹配）与 `push.js`（打分），
网页端同源在 `web/zhishi-core.js`。改任一端后必须跑：

```bash
python tools/checks/check_parity.py     # 两端同源守卫（含权重表【3b】）
node tools/checks/run_miniprogram.js    # 推送引擎回归（含非学生事项剔除断言）
```

## 九、推送决策的三处精修（本轮新增）

在"受众读准"之后，推送决策层再修了三处，让排序与版面都说得通。

### 9.1 「面向学院报送」不是学生的活儿 → INDIRECT 降权

有些通知原文就写明 `面向学院报送，非学生直接申报` —— 例：**报送转专业工作领导小组名单**。
它是**学院/老师**的活儿，学生只是被影响、不用自己办。
旧逻辑只看通知标签（"转专业"）就给它 `机会类 +14`、`面向本科生 +10`，把它顶到第 2 名。

现在：命中这些信号词 → 给 `INDIRECT = -14` 降权，且**不再**给机会类/身份正权。

```
面向学院报送 / 非学生直接申报 / 由学院统一 / 学院汇总报送 / 各单位报送 / 部门报送 / 报送材料 / 二级单位报送
```

**对照**：真·学生事项（如"本科生转专业线上申请开始"）仍照常给 `OPPORTUNITY`。

### 9.2 版面（tier）改由分数决定 → 消除"高分小卡"矛盾

旧 `tierOf` 只看倒计时（`pushLevel`），于是：
- 一条"无截止但分数 60"的转专业通知 → 进 minor（小卡）
- 一条"三天内、分数 58"的考试安排 → 进 major（中卡）

**分数高的反而版面小**，与"按分数排序"自相矛盾。

现在：**紧急（三天内）或分数 ≥ 35**，都给中卡；其余小卡。判据从"只认紧急度"改成"紧急度 ∪ 高分"。
→ 排在前面的分高条目，版面也大，排序与版面自洽。阈值常量 `MAJOR_SCORE = 35`
（`MAX_RAW` 从 100 提到 150 后同比下调，见 11.2）。

### 9.3 `PRIORITY` 理由文案如实化

`PRIORITY` 的分来自数据字段 `priority`（非原文措辞），
旧 label "原文标为高优先"会让人以为官方原文写了"高优先"。
改为 **"标记为较重要 · 系统按事项性质标注"**，如实说明来源。

### 9.4 效果（本科生档案实测）

| 条目 | 旧排名/分 | 新排名/分 |
|---|---|---|
| 报送转专业领导小组名单 | 第 2 名 / 60 | **第 9 名 / 22**（INDIRECT 生效） |
| 期中考试安排（三天内） | 第 1 / 78 | 第 1 / 78（头条） |
| 中卡 / 小卡分布 | — | 6 中卡 + 3 小卡（分数与版面一致） |

### 9.5 回归守卫

```bash
node tools/checks/run_miniprogram.js    # 473 项（含 INDIRECT / tier 自洽 / 版面无倒挂 / 已读删除 / 过期降权）
python tools/checks/check_parity.py     # 学院报送信号词 8 项两端一致 + MAJOR_SCORE / MAX_RAW 两端一致
```

## 十、已读 / 未读 与 删除（端上用户状态）

推送流有了主次，还得让用户自己"看完划掉"。这一版给通知加了**已读/未读标识**和
**删除**——都存本地，不影响别人，也不污染推送评分。

### 10.1 状态存在哪

新建 `miniprogram/utils/readstate.js`，一份本地 storage（`zhishi_read_state`）：

```json
{ "readIds": ["...最近 500 条..."], "hiddenIds": ["...最近 500 条..."] }
```

- `markRead / markUnread / toggleRead / isRead` —— 已读
- `hide / unhide / toggleHidden / isHidden` —— 删除（本地隐藏）
- `decorate(items)` 给每条注入 `read` / `hidden` 布尔
- `visible(items)` 过滤掉已删除
- `stats(items)` 出 `{ read, unread, hidden, total }`，`unreadCount` 出未读数

> **为什么不复用 `push.js` 的 `openedIds`**：那个是**反馈闭环痕迹**（点开过 → 下次
> 降权），语义是"引擎用它揣摩你的兴趣"；已读是**用户自己的书签**，语义是"我看过了"。
> 两件事混一份数据，会互相误伤——所以单开一个模块。

### 10.2 界面上怎么体现

| 位置 | 未读 | 已读 | 删除 |
|---|---|---|---|
| 首页中卡/小卡 | 左上角红点「未读」 | 卡片整体变淡 + `✓ 已读` 标签 | 长按卡片 → ActionSheet → 删除 |

## 十一、推送排序的四项精修（本轮）

上一轮把"受众读准"和"版面"理顺了。这一轮拿真实数据跑，发现四个**排序层面的硬伤**，
逐个修掉。

### 11.1 过期条目不再是"待办" → EXPIRED 系统性降权

**问题**：已截止的条目（`countdown < 0`）没有系统性降权，靠 `SUBSCRIBED(16)` +
`OPPORTUNITY(14)` 堆到 **54 分**，排在真正还要办的事前面。实测：

| 条目 | 旧位置 | 问题 |
|---|---|---|
| 国家励志奖学金评审结果公示及材料补交 | 第 3 名 / 54 分 | `cd = -1`，昨天就截止了 |
| 第八周专业课考试安排 | 第 8 名 / 24 分 | `cd = -9`，9 天前就考完了 |
| 报送转专业领导小组名单 | 第 9 名 / 22 分 | `cd = -1`，已截止 |

**修法**：`cd < 0` 时

1. 只给 `EXPIRED` 负权（`-40` 起，**随过期天数递增**，最多再压 30）——
   刚过期的（可能还能补交）比过了很久的排前面；
2. **不再给** `OPPORTUNITY / FRESH / MATCH_LEVEL / VERIFIABLE` 这些"它还值得你行动"的
   正向理由 —— 都过期了还说"可参与/面向你"是误导；
3. 一句话理由强制为 **"已截止 N 天"**（定性事实不能被正权子标签盖过）。

排序用未夹零的 `pushRaw` 做同分细分，保证"同为 0 分的过期条目"里，
`已截止 1 天` 排在 `已截止 9 天` 前面。

> 过期条目**仍留在流里**（不删），只是单列成"已截止 · 可回看"段 ——
> 方便回看结果或补交材料。

### 11.2 分数刻度校准 → 消除大片并列

**问题**：一个"满分条目"的正权之和可达 `40+22+18+16+14+10+10+8+6+4 = 148`，
但归一化分母 `MAX_RAW = 100`，于是**很多条一起顶到 100 饱和**。
实测 4 条并列 54 分，看不出谁更该先办。

**修法**：`MAX_RAW` 从 100 提到 **150**（略高于真实上限），分数全程落在 0-100
且不挤顶。同步把中卡阈值 `MAJOR_SCORE` 从 50 下调到 **35**（`50/100 ≈ 35/150`，
保持"多高才算值得占大版面"的**实际门槛不变**）。

> 两个常量都写死为整值，避免将来加规则时分数整体漂移。

### 11.3 「说明类」不是待办 → EXPLAIN_ONLY 降权

**问题**：`关于智慧安农门户页面打开缓慢的说明` 这种**告知类**通知，
因为 `event` 被分到"选课"，白吃到 `OPPORTUNITY(14)` 正权，排到第 13 名 / 25 分。
它根本没有"要你去做的一件事"。

**修法**：**无截止日期**且标题命中 `说明/澄清/解读/答疑/问答/公告栏/温馨提示/情况反映/意见征集`
→ 给 `EXPLAIN_ONLY = -18`，且不再给机会类正权。

> **例外**：有截止日期的"说明"不视为纯说明（可能是"材料补交说明"，那确实是待办）。
> 效果：该条目 25 分 → **4 分**，掉到接近底部。

### 11.4 远期软信号打折 → 时间始终主导

**问题**：`关于2025级本科生第二学期选课工作的通知`（`cd = 38`，38 天后才截止）
靠 `MATCH_GRADE(18) + OPPORTUNITY(14) + SUBSCRIBED(16)` 堆到 **48 分**，排第 2，
压过 `cd = 5` 的讲座和 `cd = 3` 的考试 —— **远期条目靠软信号反超近期条目**。

**修法**：`cd > 14` 的条目，**软信号（`OPPORTUNITY` / `FRESH`）权重减半**。
近截止的条目天然拿 `DUE_*` 正权，远处的拿不到；软信号再全额叠加就会倒挂。

> **保守的边界**：不做"7 天内必须压过一切"——那太严。一条"38 天后但点名你年级、
> 且你订阅的竞赛"确实更"为你而设"，让它排在一场泛泛讲座前面是合理的。
> 要守的是 **"紧急不能被淹"**（三天内必压过远期），不是"一切按倒计时排"。

## 十四、「各花入各眼」学院归属规则（本轮 · 用户点出的跨院误推）

### 14.1 问题：工学院的考试安排，推给了信院学生

用户原话：

> "机械与车辆工程学院 2026-2027 学年第一学期**第十周考试安排** …… 这个你给信院推送干什么？
> 我给你一个思路，每个学院都有他们自己的官网，你明白不，**各花入各眼**。"

复现：那条通知发布在**工学院官网**（`gxy.ahau.edu.cn`），考的是车辆工程各班
（原文写着 `23车辆工程-3班 汽车试验学`），但它的 `audience` 是"**未点名具体对象**"。

→ 于是被推给了**所有学院**的学生，包括信院。**根因：缺"学院归属"这一维。**

### 14.2 规则：来源即归属，学院官网只喂本学院

> **一条通知发布在哪个单位自己的官网上，本身就说明了"它是给谁看的"。**

新增 `identity.noticeCollege(n)` + `identity.matchCollege(n, profile)`：

| 来源类型 | 归属 | 可见范围 |
|---|---|---|
| **学院自有官网**（机械与车辆工程学院/工学院、经济管理学院、信息与计算机学院…） | 该学院 | **只推给该学院学生**；其他学院 ❌排除 |
| **校级单位**（图书馆 / 校工会 / 教务处 / 本科生院 / 学工处 / 保卫处 / 数据管理处 / 创新创业学院…） | 校级（`''`） | **全校可见**，不设限 |
| 认不出的来源 | 校级（`''`） | 放行（不误判） |

**三重防误杀**（错杀一个真机会，比多推一条的代价高）：

1. 用户**没填学院** → 放行（只在"能确定归属 + 填了别的学院"时才排除）；
2. 通知**标题/受众明写"全校 / 全体师生 / 各学院各单位"** → 即便发在学院站点也当全校可见；
3. 来源认不出是哪个学院 → 当校级，放行。

**别名表**（`SOURCE_COLLEGE_ALIAS`）：把来源串里的学院名（含简称/旧名，如
"机械与车辆"→工学院、"信息与计算机学院"→信息与人工智能学院）归一到 `COLLEGES` 标准名；
`UNIVERSAL_SOURCE_KW` 列出校级单位关键词。**两张表两端（小程序 + 网页）逐项一致，由 `check_parity.py` 守卫。**

### 14.3 推送理由也跟着变

推送引擎（`push.js` / `zhishi-core.js`）的 `MATCH_COLLEGE` 理由，除了"正文点名了你的学院"，
现在还支持"**来自 XX 官网 —— 是你所在学院发布的通知**"（当通知就发在你所在学院的站点上）。

## 十五、多信息源现网复抓与抓取链路修复（2026-11-07）

一轮"多信息源抓取 → 推送系统验证"的实测，修掉三处会让数据失真或让推送失效的根因。

### 15.1 相对链接解析错误（详情页 404）

安农二级站的详情链接有两种写法：

| 站点 | href 形态 | 旧结果 | 新结果 |
|---|---|---|---|
| 信院/工学院/工会/保卫处/人事处 | 绝对 `/info/1151/6161.htm` | 200 | 200 |
| 经管 | 相对 `../info/1101/25926.htm` | **404** | 200 |
| 图书馆 | 相对 `../../info/2401/55481.htm` | **404** | 200 |

旧代码按站点根硬拼 `base + href`，把 `../` 保留成字面路径：

```
✗ 旧：https://jgxy.ahau.edu.cn/../info/1101/25926.htm  → 404
✓ 新：https://jgxy.ahau.edu.cn/info/1101/25926.htm     → 200
```

**修复**：`parse_list` 改用 `urljoin(列表页地址, href)`。
**效果**：抽查 25 条详情页 **25/25 全部 200**；图书馆活动通知 5 → 20 条。

### 15.2 正文模板噪声（污染信息真实性）

详情页会在正文前后混入同一套导航/元信息：

```

上一条：xxx 下一条：xxx 版权所有 © 安徽农业大学 皖ICP备...
```

**修复**：新增 `denoise_body()`（噪声前缀 / 内联元信息正则 / 面包屑三段清洗）。
**效果**：`请输入您搜索的信息` 4→0；`网站首页` 24→0；`上一条/下一条/作者/发布时间` 约 30→0。

### 15.3 来源单位映射错误（学院归属失效）

注入脚本 `inject_real_into_mp.py` / `inject_real_into_web.py` 按短码 `gxy` 查表，

## 十八、自定义关键词订阅（本轮 · 用户："我输入这个正大杯，以后有相关通知就主动推给我"）

### 18.1 为什么要加这一层

固定 9 类标签是**我们替你分好的类**——覆盖不到某个具体赛事、某个项目、某个实验室。
学生真正在意的东西常常是一个**具体名词**：

> 正大杯 · 挑战杯 · 数学建模 · 蓝桥杯 · 节能减排 · 大创 · 四六级 · 招聘会 · 交换生…

这些词如果不在标签词表里，旧逻辑下就**永远推不过来**。
所以给用户一个输入框：把任意关键词存进 `PROFILE.keywords`，
池子里凡命中该关键词的通知，都算"与我有关"，进推送流并走主动推送。

### 18.2 单一事实源

关键词的"匹配"逻辑抽在 **`miniprogram/utils/subscribe.js`**（无依赖纯函数层）：

| 函数 | 作用 |
|---|---|
| `normKeyword(k)` | 归一化：去所有空白 + 转小写（英文/数字大小写不敏感） |
| `noticeHaystack(n)` | 一条通知的"可命中文本"（小写）：标题 / 浓缩 / 要点 / 标签 / 来源 / 原文 |
| `keywordList(profile)` | 用户关键词的归一化去重列表 |
| `matchKeyword(n, profile)` | 命中哪个关键词（返回**最长**的那个，最说明问题）；没命中返回 `''` |
| `hitKeyword(n, profile)` | 布尔版，供候选池过滤 |
| `sanitizeKeywords(arr)` | 保存前清洗：去空白 / 截断 20 字 / 去重 / 最多 12 个 |

**为什么独立成层（而不是塞进 push.js 或 store.js）**：
`push.js` 需要它（算 `KW_MATCH` 理由），`store.js` 也需要它（筛候选池）。
若写在 `push.js` 里，`store.js` 就得 `require push.js`，而 `push.js` 已 `require store.js`
—— 形成**循环依赖**，小程序模块缓存下会拿到半初始化的空对象（真会出诡异 bug）。
抽成无依赖层后，双方各自 `require`，谁也不依赖谁。

网页版 **`web/zhishi-core.js`** 里有**同名同义**实现（`check_parity.py` 的 `【3c】` 逐项守卫）。

### 18.3 命中口径（与检索层同源）

命中范围 = **标题 / 浓缩一句话 / 要点 / 标签 / 来源单位 / 原文** —— 与 `search.js` 完全一致。
之所以必须一致：否则会出现"**搜索搜得到、订阅却推不到**"的分裂，用户会觉得系统坏了。

长词优先：用户同时订了「杯」和「正大杯」，命中"正大杯通知"时理由里写**「正大杯」**（更具体）。

### 18.4 候选池的 OR 逻辑（真修复点）

旧代码把"与我有关"写成 `interests.indexOf(n.event) >= 0`，抄了 5 遍。

```
候选池 = (命中订阅标签 || 命中自定关键词) && 过身份/学院过滤
```

## 十九、信息源重构：注册表驱动 + 可插拔适配器（v2）

### 19.1 为什么要重构

上一版的采集器 `collect_notices.py` 把「有哪些站点、每个站点怎么翻页、怎么解析」
全部硬编码在一个 `TARGETS` 列表里。三个后果：

1. **来源畸形**：某站翻 10 页、某站翻 1 页，写死之后图书馆吃掉 66 条、校工会吃掉
   45 条，占了池子一半——而图书馆的"开馆时间调整"、校工会的"教职工体检"对学生
   几乎零价值。
2. **陈年污染**：官网翻页 `/index/tzgg/N.htm` 会一路翻到 2010 年的存档，池子里混进
   2010-2012 的通知，时间线跟"知时"的当下完全错位。
3. **接入成本高**：想加一个学院、想接"数智安农"，都要改主流程。

v2 把这三件事拆开：**配置归配置、适配归适配、主流程归主流程**。

### 19.2 三层架构

```
data/sources.json  ── 声明「有哪些源、每个源怎么取」
        │
        ▼
   SourceRegistry  ── 读注册表，按 adapter 名选解析器
        │
        ▼
     adapters/     ── 每种模板一套解析器
        │
        ▼
     Collector     ── 只管翻页 / 去重 / 闸门 / 落盘
```

主流程 `collect()` **不知道任何源长什么样**——它拿到的是适配器对象，只调
`adapter.list_items()` 和 `adapter.detail_text()`。

### 19.3 源注册表 data/sources.json

每个源声明这些字段：

| 字段 | 含义 |
|---|---|
| `id` | 源唯一标识（如 `jwc_wzsy`） |
| `site` | 展示名（如"本科生院（教务处）· 通知公告"） |
| `adapter` | 用哪个解析器（`ahau_vsb` / `generic` / `szsn_api`） |
| `list_url` / `base` | 列表页地址 / 站点根 |
| `pages` | 向后翻几页 |
| `per_site` | 单源条数上限 |
| `audience` / `campus_units` | 受众标签 / 归属学院（供"各花入各眼"用） |
| `enabled` | 是否启用 |

**新增一个安农二级站** = 在 `sources` 里加一条，主流程零改动。
**关掉一个牛马源**（如校工会）= 改 `enabled: false`，一条配置。

### 19.4 适配器

| 适配器 | 适用 | 要点 |
|---|---|---|
| `ahau_vsb` | 安农 Visual SiteBuilder 模板（绝大多数二级站） | 列表页 `a[href]` 命中 `/info/<栏目>/<文章>.htm`；详情正文在 `div.v_news_content`；**日期三重兜底**（同 parent → 前后兄弟节点 → 详情页"更新日期"） |
| `generic` | 任意静态列表页 | 相对链接解析兜底 |
| `szsn_api` | ★ 数智安农（预留） | 见 19.7 |

日期兜底是必要的：`xslt`（学生报告）站的日期在**兄弟 li** 里而不是同一个 parent，
不兜底就会全部无日期。

### 19.5 两道入库闸门

**时效闸门**（`FRESH_AFTER = "2025-01-01"`）：
日期早于此阈值的通知**直接丢弃，连详情都不抓**。实测清掉 241 条 2010-2024 存档。

**价值过滤**（`LOW_VALUE_RE`）：
命中"房产出租 / 招标公告 / 中标公示 / 采购 / 资产处置"等模式的条目，抓到了也不入库。
实测挡掉官网 `tzgg` 栏目的全部资产处置文书。

这两道闸门是"信息源完全是错的"的直接解药——第一道治时间错位，第二道治内容错位。

## 二十、自查自纠：数据流水线的四类缺陷修复（本轮 · 用户："作为一个只要能接入信息源就可以分类推荐工作的小程序，进行全面优化和自查自纠"）

用户把目标一句话讲清了：**信息源是可插拔输入，分类推荐是自动化输出，两者必须解耦**。
本轮围绕这个目标做了一轮端到端自查，用两个审计脚本（推送流质量 / 重复与误分类）扫全池，
暴露并修掉了四类真实缺陷。全部改动集中在**采集层**（`collect_notices.py`）与
**理解层**（`inject_digest_into_mp.py` / `push.js` / `identity.js`），主流程零新增概念。

### 20.1 缺陷一：列表无日期源 → 时效闸门形同虚设（陈年条目蒙混入库）

**症状**：推送流里混进 2018/2019 年的旧通知 ——
「周一 292019.04 知否知否…Emerald杯第七届」（2019）、
「周三 252018.04 …Emerald杯第六届」（2018）、
「周五 182019.01 书香江淮第五届」（2019）。

**根因**：图书馆（lib）与学生报告（xslt）两个站的**列表页没有日期列**，
而且把日期**编码进了标题**（`周一292019.04` = 周一 29 号 · 2019.04）。
旧流程里：
1. `_find_date_near()` 取不到列表日期 → `it["date"] = ''`；
2. 时效闸门判 `if it["date"] and it["date"] < FRESH_AFTER` → 空串直接放行（**闸门失效**）；
3. 详情页回填 `_detail_date()` 拿到的是**模板渲染日**（xslt 一律 `2026-11-07`），
   把真实年份彻底掩盖。

**修复**（`collect_notices.py`）：
- 新增 `_title_date()`：从标题里解析四种"编码日期"写法 ——
  `周X<日><年>.<月>[.<日>]`、`周X<年>.<月>.<日>`、`X月Y日`（无年份归本年）、`M.D`（同上）；
- `_monthday_to_date()`：无年份的月日 → 本年；若已过去 >60 天判为明年（跨年预告）；
- `list_items()` 里**先从原始标题抽日期存进 `it["title_date"]`，再剥离前缀** ——
  否则前缀一剥，唯一的时效线索就丢了；
- 时效闸门改用 `gate_date = it["date"] or it["title_date"]`；
- 详情日期回填**降级为最后兜底**：只有列表日期、标题日期都拿不到时才用详情页日期
  （因为详情页日期常是模板抓取日，可信度最低）。

### 20.2 缺陷二：党政会议新闻占满学院"工作动态"栏

**症状**：经管学院（jgxy）贡献的几乎全是「纪委召开工作会」「巡察整改监督小组会议」
「党委理论学习中心组学习会」「全体教职工大会」——同一标题的不同场次反复出现，
学生端看到成串无意义卡片。

**根因**：`jgxy` 原本指向的 `jjgz/gzdt.htm` 是**学院党政工作动态**栏，
不是学生向通知栏；且这类会议新闻对学生的价值为零。

**修复**（双管齐下）：
1. **换源**：`data/sources.json` 里 `jgxy.list_url` 从 `jjgz/gzdt.htm`（工作动态）
   换成 `index/tzgg.htm`（**通知公告**）—— 实测该栏才是学生向内容
   （职业规划大赛院级选拔、种时光助学金推荐、开学补考缓考安排、推免工作、国奖评审细则）。
2. **入库前过滤**：新增 `NONSTUDENT_NEWS_PATTERNS`（纪委会议/巡察/党建/主题党日/
   理论学习中心组/教职工大会/校长办公会/工会活动/离退休/关工委/校友会…），
   命中即丢；用 `_headline()` 取**精简标题**判定，避免原始标题把正文拼进来时
   误带"学生"二字导致豁免失效（这是修这条时踩的第二个坑）。

### 20.3 缺陷三：同名条目重复（跨栏同稿 + 同题多场次）

**症状**：推送流里同一篇文章出现两次（同稿在图书馆「新闻公告」「活动通知」两栏各发一遍），
或同一标题的不同场次各占一张卡。

**修复**：新增 `dedup_by_title()` —— 按 `clean_title` 归并，同名保留日期最新的一条，
在主流程 `collect()` 之后、落盘之前统一去重（本轮合并 3 条）。跨源、跨栏的同名稿一并收口。

### 20.4 缺陷四：事后公示误吃"机会"正权 + 标题残留噪音

**症状**：
- 「十佳班集体评选结果公示」被归 奖助学金 且吃到 `OPPORTUNITY(14)` 正权 ——
  但它是**事后结果公示**，不是"能报名"的机会；
- 「从青年基金看基础研究和人才引进（二）」被误归 奖助学金 —— 因正文"基础研究资助"
  命中过宽的 `资助` 关键词；
- 列表页「了解更多 / 值班安排表」等噪音并进标题。

**修复**：
1. **`push.js` / `zhishi-core.js`（同源两处）**：`isExplain` 判定扩词 ——
   无截止日期 + 标题含 `公示|名单公布|结果公布|评审结果|复核结论` → 判为"只是说明，非待办"，
   给 `EXPLAIN_ONLY(-18)` 且**跳过 OPPORTUNITY**。
2. **标签词表三处同源**（`collect_notices.py` / `inject_digest_into_mp.py` /
   `miniprogram/utils/tags.js`）：奖助学金关键词把过宽的 `资助` 收窄为
   `学生资助|资助政策|资助育人|困难生|绿色通道`，消除"基础研究资助"误命中。
3. **`clean_title()`**：新增 标题天然终点（…的通知/公告/公示、根据《…、为做好…、
   各班级：…、了解更多/查看详情 尾缀）截断，标题恢复可读。

### 20.5 缺陷五：`noticeCollege` 把"讲座/论坛"当校级 → 学院讲座跨院误推

**症状**：给小程序的学院归属自查脚本发现 —— 「经济管理学院学术讲座」这类
**发布在经管官网**的通知被判成"校级"，导致别的学院学生也收到。

**根因**：上一轮为了让"学生报告/学术讲座"频道不按学院设限，把 `讲座|论坛|讲堂|沙龙`
加进了 `UNIVERSAL_SOURCE_KW`；但 `noticeCollege()` 判定时把 **来源 + 标题**拼在一起
去匹配这个表 —— 于是标题里的"讲座"二字把一个明确来自经管官网的通知误判成校级。

**修复**（`miniprogram/utils/identity.js` 与 `web/zhishi-core.js` 同源两处）：
`noticeCollege()` 判"是否校级"时**只看来源串**（`n.source`），不再并入标题；
学院识别仍用 来源+标题 兜底。这样"学生报告频道"仍按来源判为校级，
而"经管官网发的讲座"正确归经管学院。

### 20.6 顺带修正的两处标注错误

## 二十一、受众抽取精细化：别让"未点名"吃掉可分类的通知（本轮 · 用户："小程序继续优化"）

### 21.1 遇到的问题

自查受众抽取后发现：**123 条里 22 条（约 18%）被打成"未点名具体对象"**。
但逐条看进去，这 22 条里混着两类**明明能判、却被漏判**的通知：

| 类型 | 例子 | 旧标签 | 该有的标签 |
|---|---|---|---|
| 图书馆/文献活动 | "ProQuest 杯外文文献检索答题大赛" | 未点名 | 面向全校学生 |
| 校园选拔赛 | "ERP 数智化运营大赛校园选拔赛" | 未点名 | 面向全校学生 |
| 教职工事项 | "新入职教师岗前培训"、"高层次人才认定公示" | 未点名 | 在职教职工 |

**危害**：① 学生漏收了"可参与的竞赛/活动"（本该进推送流的机会类）；② 教职工事项被当成人人可见的"通用通知"，学生看到会困惑"这不是给我办的"；③ 身份筛选失去了把它们从学生流里摘出去的能力。

### 21.2 修复：在退回"未点名"之前，先判两类

在 `pick_audience` 的兜底分支里，**按顺序**补三条识别（顺序很关键——先学生向、再教职工向）：

| 顺序 | 规则 | 输出受众 | 关键约束 |
|---|---|---|---|
| ① | **图书馆活动**（`LIB_ACTIVITY_PATTERNS`） | `全校本科生、研究生（图书馆活动）` | 排除"开放安排/闭馆/值班表"这类服务性通知（谁都能看） |
| ①b | **校园选拔赛/竞赛**（`COMPETITION_PATTERNS`） | `全校本科生、研究生（竞赛选拔）` | 排除"考务/考点/监考/评委"等赛事**保障工作**（那是教职工的事） |
| ② | **教职工/行政事项**（`STAFF_ITEM_PATTERNS`） | `在职教职工` | 排除学生向的"招聘"措辞（招聘会/校园招聘/求职/宣讲会）——那是给学生办的 |

**用"全校…"打头的巧思**：竞赛即便挂在某学院站点，也是面向全校报名的。
受众值以 `全校` 开头，`matchCollege` 的"全校豁免"就会放行——
否则"经管学院办的 ERP 校赛"会被"各花入各眼"挡在信院学生之外（已踩到，见 21.4）。

### 21.3 效果

| 指标 | 优化前 | 优化后 |
|---|---|---|
| "未点名具体对象" | 22 条 | **11 条** |
| "在职教职工" | 0 条 | **8 条** |
| 图书馆活动（新） | — | **3 条** |
| 竞赛选拔（新） | — | **2 条** |

剩下 11 条"未点名"经复核**确属无法判断**（ESI 期刊目录、学术评价讲座、图书馆值班表/开放安排、停车库施工、交通安全提示）——这些退回通用标签是**诚实的**，不硬凑。

### 21.4 踩到的坑：新受众被"各花入各眼"挡掉

加了 `在校本科生、研究生（竞赛选拔）` 后，`run_miniprogram.js` 报错：
**"真实数据里「本科生+研究生」并列条目对本科生放行" 失败**。

根因：ERP 校赛发布在**经管学院官网**，`noticeCollege` 判出归属经管学院 →
`matchCollege` 用"各花入各眼"把信院学生挡在外面。
但这明明是一场**面向全校**的选拔赛，不该被学院归属限制。

修复：受众值**改用 `全校本科生、研究生（…）` 开头**（而非 `在校…`），
命中 `matchCollege` 里的 `/全校/` 豁免规则 → 放行。这也与既有并列受众口径完全一致。

## 二十二、真·触达：从"你来找它"到"它来找你"（本轮 · 用户质疑"这个到现在只是一个空架子"）

### 22.1 用户点出的真问题

用户看完后一针见血：**"这个目前好像没有办法解决痛点。"**

痛点原文是我们自己写的——"**信息存在，但到达不了该看到它的人手上**"。
而在此之前，我们的"推送"其实是：**你打开页面，它才按分数把通知排好**。
不开页面，它什么都不发生。换句话说，它是"**一个更好看的通知聚合页**"，
不是它宣称的"**会主动找你的雷达**"。**差的就是"到达"这一步。**

诚实地讲清楚：**没有主动触达，痛点没被解掉，只是被整理了一遍。**

### 22.2 取舍：为什么不能简单地"接个服务器就完事"

大赛要求原创代码类路径 2 的作品**必须能现场断网演示**（双击即开、零依赖）。
而真正的定时推送需要**服务器常驻**。两件事天然冲突。

所以方案（用户选定的"第二条"）：**把痛点补到"演示级可达"**——
不等真服务端上线，先做出**可验证的触达闭环**：机制完整、当场能演、答辩不翻车。

### 22.3 新增的三层东西

| 层 | 文件 | 作用 |
|---|---|---|
| **微信订阅消息层** | `miniprogram/utils/wxnotify.js` | ① 授权：`wx.requestSubscribeMessage`（合规硬要求，必须用户本人点）；② 登记：把订阅类别 + 提前量写进云端；③ 回执：记录送达留痕。**无模板 ID 时如实降级为"演示模式"，不冒充已通。** |
| **触达时间线引擎** | `miniprogram/utils/reachlist.js` + `web/zhishi-core.js`（`buildReach`） | 把一条通知从**发布**到**截止**的全过程摊在时间轴上，标出**哪一天会主动找你、找你几次**。不产生新数据，完全由真实条目算出 → **可推演、可复核、可离线跑**。 |
| **页面落点** | `pages/push/*`、`pages/me/*` | 推送设置页与订阅页各加"微信服务通知"入口（授权、提前量、留痕）+ "触达时间线"可视化。 |

### 22.4 触达时间线的三条硬规则（与推送引擎同口径，避免"说一套做一套"）

1. **只有"与我有关"的条目才进规划**——有推送理由（身份/订阅标签/自定关键词）即算相关；
2. **提醒日 = 截止日往前推 advance 的每一档，且不早于发布日**——发布前不可能提醒；
3. **已过期的不再规划任何提醒**——避免"教人去赶一个已经关了的门"。

> 提前量可选：**截止前 7/3/1 天**（最稳）/ **3/1 天**（推荐）/ **仅 1 天**（最少打扰）。

### 22.5 实测产出（真实数据 · 123 条）

推送设置页渲染（信院本科生档案）：

```
微信服务通知 · 关掉页面也能提醒你
  当前状态：未开启          [演示模式]
  提前几天提醒：截止前 3 / 1 天（推荐）
  送达留痕：0 次（暂无）
  [开启微信服务通知]  [模拟一次主动送达]

触达时间线 · 什么时候会主动找你
  与你相关 123 条 · 已规划提醒 20 条 · 未来 14 天内会打扰 14 次
  11月8日  2 条 | 11月9日  4 条 | 11月10日 2 条 | 11月12日 2 条 | 11月13日 2 条 …
```

每一组都写明**来源 + 截止日 + 剩几天**——评审能逐条核对"它到底是哪天找的我"。

### 22.6 合规边界（本层的红线）

- **绝不静默订阅**：必须由用户点按钮触发 `requestSubscribeMessage`；
- **授权失败 / 用户拒绝 / 模板未配置** → 一律**如实降级**为"仅应用内推送"，不假装能推；
- **只登记身份标签 + 订阅类别 + 提前量**，不读取任何私域数据；
- 演示模式在页面**明确标注**，配置模板 ID 后自动转真，**用户无需重新操作**。
