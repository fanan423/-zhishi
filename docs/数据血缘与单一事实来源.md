# 数据血缘与单一事实来源（SSOT）

> 建立日期：2026-11-15 ｜ 对应评估报告「四份数据文件口径不一、靠脚本顺序约束而非单一事实来源」扣分点
> 本文是**内部工程契约**，同时可直接摘进说明文档第五章「知识库构建说明」。

---

## 〇、先纠正一个理解

评估报告写「`data/notices.json` 42 条 / `notices_app.json` 114 / `notices_merged.json` 114 / `miniprogram/data/notices.js` 123，口径不一」。

复核后：**这不是数据错乱，而是四个角色不同的池被误当成同一份数据的四个副本。** 真正的问题是——这些角色此前只靠「脚本执行顺序」隐式约定，没有写成显式契约，改数据时容易漂移。

因此本次优化不是「把四个数字改成一样」，而是：
1. 明确定义每个文件的角色与派生关系（本文）；
2. 把「谁从谁派生、谁该等于谁」写成机器断言（`tools/checks/check_data_lineage.js`）；
3. 把「改数据后必须按什么顺序重建」固化成一条命令。

## 二、角色定义（逐一）

| # | 文件 | 角色 | 允许与其它文件不同吗 | 谁写它 |
|---|---|---|---|---|
| ① | `data/notices_real.json` | 采集底本，schema v2，含 `site_status` 健康度；**条目用 `source_id`，尚未编号** | 是（它是源） | `collect_notices.py` |
| ② | `data/notices_app.json` | ① 的下游消费副本，按 `real-NNN` 编号 | **否，条数与 URL 集合必须等于 ①** | `collect_notices.py` |
| ③ | `data/notices_merged.json` | ① 的兼容副本（旧脚本按此名读） | **否，条数与 URL 集合必须等于 ①** | `collect_notices.py` + `reclean_titles.py` |
| ④ | `data/notices.json` | Demo 合并池（真实 + 演示样例 + digest） | 是（角色不同：合并层） | `merge_real_into_demo.py` |
| ⑤ | `miniprogram/data/notices.js` | **SSOT**：小程序与所有网页形态的唯一数据源 | 是（它是端上真源） | 注入/理解/清洗脚本 + `export_llm_fields.js` |
| ⑥ | `web/zhishi-data.js` | ⑤ 的自动导出 | **否，必须等于 ⑤** | `export_mp_data_to_web.py` |
| ⑦ | 各 HTML | 构建产物，内联 ⑥ | **否，KPI 必须现算自 ⑥** | `build_*.js` / `build_demo.py` |

**关键判定**：①②③ 三者必须同条数、同 URL 集合（① 用 `source_id`、②③ 才编号，故用 URL 作稳定键）；⑤⑥ 必须同条数、同 id 集合、同 llm 产物条数；⑦ 的 KPI 必须现算。
①②③ 与 ⑤⑥ **不要求相等**——前者是「抓回了什么」，后者是「端上最终用了什么」，中间经过合并、价值过滤、理解层、标题清洗。这正是之前看起来「口径不一」的真相。

> 注：① 的条目没有 `id` 字段（采集器只给 `source_id`），`real-NNN` 是下游 ②③ 才编的号。
> 守卫因此用 **URL 集合** 比对 ①②③，用 id 集合比对 ⑤⑥。早先按 id 比对会误报「121 条全是 undefined」，
> 属于把 schema 差异当成数据漂移 —— 已修正。

## 三、本次实测基线（2026-11-15 重跑采集后）

| 文件 | 条数 | 说明 |
|---|---|---|
| ① `notices_real.json` | 121 | 11 个源正常，WAF 拦截源如实记录 |
| ② `notices_app.json` | 121 | = ① |
| ③ `notices_merged.json` | 121 | = ① |
| ④ `notices.json` | 148 | 真实 + 演示样例的合并层 |
| ⑤ `notices.js` | 130 | 真实 124 + 演示 6，其中 **46 条带 llm 产物** |
| ⑥ `zhishi-data.js` | 130 | = ⑤ |

> 这些数字会随每次采集变化，因此**断言只校验「相等关系」，不校验具体数值**——这正是防止硬编码漂移的设计。

## 四、为什么这不叫「四份数据冗余」

| 常见误解 | 实际 |
|---|---|
| 「四份文件存了四份数据，改一份忘三份」 | ②③ 是 ① 的同次写出副本（同一脚本一次落盘），不是人工维护的四份 |
| 「改成一份就好了」 | ④ 是合并层（含演示样例与 digest），⑤ 是端上结构化层（含受众/截止/llm），字段结构完全不同，无法合并 |
| 「脚本顺序约束不可靠」 | 已改为**机器守卫**：`check_data_lineage.js` 校验相等关系，`check_parity.py` 校验两端算法同源，`check_kpi_sync.js` 校验物料 KPI 现算 |

## 五、改数据的标准动作（顺序不可乱）

```powershell
$env:PYTHONIOENCODING = "utf-8"
$py = "C:\hclaw\python\python.exe"   # 项目约定的解释器，自带 requests/bs4/docx/lxml

# ① 采集（刷新 ①②③）
& $py tools\collect_notices.py
& $py tools\reclean_titles.py
& $py tools\merge_real_into_demo.py        # ④
& $py tools\inject_real_into_mp.py         # ⑤ 裸原文
& $py tools\inject_digest_into_mp.py       # ⑤ 理解层抽字段
& $py tools\fix_mp_titles_tags.py          # ⑤ 清洗
& $py tools\build_rawdata_page.py

# ② 重跑采集会重编 id → 必须重建 LLM 回流基线（否则回流器的改动保护会误拦）
node tools\agent\reset_llm_baseline.js

# ③ 真调大模型 → 产物回流（可选，但要留证据就跑）
$env:AGENT_SOURCE = "local"
node tools\agent.js --llm --limit 36
node tools\agent\export_llm_fields.js

# ④ 同源导出 + 重建全部对外形态
& $py tools\export_mp_data_to_web.py       # ⑥
node tools\build_app.js                    # ⑦ 知时.html
& $py tools\build_demo.py                  # ⑦ 交互Demo.html
node tools\build_portal.js                 # ⑦ 知时门户.html
node tools\build_presentation.js           # ⑦ 知时_演示版.html
node tools\sync_promo_kpi.js               # ⑦ 宣传物料 KPI 现算同步

# ⑤ 全量自检（含血缘守卫 / 同源守卫 / KPI 守卫）
node tools\checks\run_all.js
```

> ⚠️ `inject_real_into_web.py` 是**已废弃的历史脚本**：`web/index.html` 早已改为
> `var NOTICES = ZS_DATA.NOTICES`（读 ⑥），不再有可注入的数据块。它会在管线里
> 报「找不到 NOTICES 块的结束位置」，但对交付物**无任何影响**——不要为它修锚点，
> 那等于把已删掉的旧结构再装回去。已在 `tools/README.md` 标注。

## 六、机器守卫清单

| 守卫 | 校验什么 |
|---|---|
| `check_data_lineage.js`（本次新增） | ①=②=③；⑤=⑥；⑤ 中 real 条数 ≥ ① 中真实条数的合理区间；META 与 ⑥ 自洽 |
| `check_parity.py` | 小程序与网页版标签/算法/热词/学院别名逐字同源 |
| `check_kpi_sync.js`（本次新增） | 所有宣传物料与门户的 KPI = ⑥ 现算值；无写死的 156；AI 区块透传三形态 |
| `check_llm_pipeline.js` | 提示词两端同源、llm 产物字段齐全、引文如实标注、报告一致 |
| `check_daydrift.js` | 倒计时口径全链一致 |
