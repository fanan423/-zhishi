## 一、作品简介

### （〇）对标选题方向（依大赛通知四个方向）

| 项 | 内容 |
|---|---|
| **主对标** | **（二）AI+管理服务** —— 聚焦学生服务场景，提升校园管理效能 |
| **次对标** | **（四）AI+安农特色** —— 挖掘本校独有场景（9 个安农公开源接入 + 数智安农平台预留接口） |
| 对标依据 | 官方方向（二）原文举例含"**迎新/毕业服务机器人：整合入学/离校流程信息，一问即答**"——本作品正是把"多源流程信息整合 → 一问即答 / 主动送达"做实 |

### （一）项目背景

**面向用户**：安徽农业大学全体在校学生（本科生为主）；同时覆盖校园内**面向教职工**的公开通知类别（如教师培训、职称评审、人才认定等），使受众面不局限于单一身份。

**使用场景**：学生每天面对来自**教务处、各学院、学生工作处、图书馆、创新创业学院**等多个单位的公开通知。这些通知分散在不同官网、公众号与班群，学生**不知道去哪儿找、也不知道"有这回事"**，导致错过转专业、竞赛报名、评奖评优、讲座选课等关键窗口。

**问题本质**：这不是"懒"，是**信息架构问题**——信息存在，但到达不了该看到它的人手上。

### （二）项目目标

本智能体能够完成的主要任务：

1. **聚合**：定时采集多个**公网公开**通知页面的内容；
2. **理解**：用大模型把非结构化的通知原文，抽取为结构化五要素——
   **事件类型 / 适用人群 / 截止时间 / 所需材料 / 办理入口**；
3. **浓缩**：把 800 字通知压成 3 句人话，且**每个结论都挂原文出处**；
4. **匹配**：结合用户主动填写的画像（年级 / 学院 / 关注类别），筛出**与"我"相关**的通知；
5. **预警推送**：以"**谁能报 · 剩几天 · 怎么办**"三问式倒计时卡片，主动送达。

**一句话目标**：做一个**会主动找你的校园信息雷达**。

### （三）核心创新点

**团队自主设计、实现或改进的内容：**

1. **范式跃迁：从"问答检索"到"主动预警"**
   现有校园 AI 助手（如学校已有的答疑类工具）解决的是"**你问它答**"；
   「知时」解决的是"**不问也能收到**"——**判断发生在 AI 这边，不是发生在用户这边**。

2. **真·触达闭环：把"提醒"真的送到人手上（痛点兑现）**
   痛点原文是"信息到达不了该看到的人手上"。若只在应用内排序，仍是"你来找它"。
   本项目补上**微信订阅消息**这条合规通道：用户点击即调起 `wx.requestSubscribeMessage`
   取得授权 → 把订阅类别与提前量登记进云端 → 服务端在临近截止时通过微信服务通知送达，
   **关掉小程序也能收到**。在**未配置模板 ID** 时，交互与登记照走，
   但页面**如实标注"演示模式"**、绝不冒充已通——**诚实优先于好看**。

3. **可推演、可复核的"提醒时间"**
   把每条通知从**发布到截止**摊在日程上，标出**哪一天会主动找你、找你几次**。
   全部由真实"发布日 + 截止日 + 用户提前量"算出，不产生任何新数据，
   因此**能推演、能逐条复核、断网也能演示**（答辩现场可靠）。
   —— 回答了评审必然会问的一句："你说会主动提醒我，凭什么信？"

4. **理解后重构 + 全链路溯源（核心技术差异化）**
   不止搬运原文，而是**读懂再重写**：浓缩结论的每一句引文，都在原文中做**字符串定位**，
   点要点即可高亮原文对应句，点原文高亮句可跳回要点（**双向联动**），支持"一键全部高亮"。
   —— 这是"**可信的智能**"：AI 说的都能查证。

5. **主动划清数据边界（合规即竞争力）**
   对每条数据链路都实测过边界，并在 Demo 中做成可视化面板，**明确标注"教务系统后台永
   不接入"**。在同行普遍宣称"打通一切"时，主动说"我们不碰什么"，体现工程成熟度与合规意识。

6. **在线真后端：从本地演示走到可调用云推理**
   独立在线版接入免密钥云大模型与云数据库：推荐由模型实时重排，画像与运行留痕上云，
   `?selftest=1` 可现场核验 `workbuddy-cloud` 真调。演示版与参赛可用版仍为离线自包含，
   在线能力不是把离线交付改成联网依赖，而是一条可验证、可切换的补充链路。

### （四）应用价值

- **效率**：把学生每天手动翻 6 个渠道的成本，降为**看几张卡片**；
- **质量**：杜绝"漏看通知"导致的**机会成本损失**（转专业、竞赛、评奖窗口一旦错过不可逆）；
- **可落地**：数据源全部是**公网公开页**，无需校方授权即可跑通，每个学生都用得上；
- **可扩展**：理解层与匹配层解耦，未来可平移到"招聘信息雷达""政策申报通知"等场景。

```
│  注册表驱动     │   │  规则/LLM 抽取  │   │  画像 × 事件   │   │  倒计时卡片    │

└───────────────┘   └───────────────┘   └───────────────┘   └───────────────┘
        ↓                   ↓                   ↓                   ↓
   9 个安农公开源      结构化五要素         相关事件集         小程序 / 网页
   （任何人可访问）    ＋浓缩＋引文锚点      （按身份筛）        ＋提醒时间

  贯穿全程：两道入库闸门（时效闸门 + 价值过滤）· 27 个校验脚本的回归防线
```

| 层 | 职责 | 关键设计 |
|---|---|---|
| **采集层** | 定时聚合公开通知页 | **注册表驱动**（`data/sources.json` → SourceRegistry → 可插拔适配器 `ahau_vsb` / `generic` / `szsn_api`）；**仅公开源**，频率受控（详情页 `sleep(0.4)`、单站限额、翻页上限） |
| **理解层** ⭐ | 抽取五要素 + 生成浓缩要点与**引文锚点** | **本项目核心**；规则版已跑通、LLM 版接口预留（同一 `understandNotice` 契约，页面零改动） |
| **匹配层** ⭐ | 用户画像 × 事件属性 | **AI 推荐**：构建期模型按画像算相关性分 + 理由 + 引文（22/22 真调留痕），规则加权保底可解释；「**各花入各眼**」：学院官网通知只喂本学院；**不碰私域数据** |
| **提醒层** | 倒计时预警卡片 + 分类订阅 + **微信订阅消息** | 三问式呈现；应用内推送 + **真·触达**（关掉小程序也能收到）+ 提醒时间 |

|---|---|---|
| **时效闸门** | 剔除过时通知（旧闻不冒充新闻） | 发布日早于 `FRESH_AFTER = 2025-01-01` 的降权/剔除 |
| **价值过滤** | 剔除噪音（非学生事项、低价值条目） | `LOW_VALUE_RE` / `NONSTUDENT_NEWS_RE` 双正则拦截 |

### （二）业务全流程工作流（智能体实际执行顺序）

以一条真实通知为例，**从采集到送达**的完整链路：

| 步骤 | 动作 | 产出 | 关键代码 / 脚本 |
|---|---|---|---|
| 1 | **采集**：按注册表逐源抓取公开通知列表与正文 | 原始 HTML / 正文文本 | `tools/collect_notices.py` + `adapters/` |
| 2 | **过闸**：时效闸门 + 价值过滤 | 干净的候选条目 | `FRESH_AFTER` / `LOW_VALUE_RE` |
| 3 | **理解**：抽取五要素 + 受众判定 + 浓缩要点 | 结构化事件对象（含 `digestOne` / `digestPoints`） | `tools/inject_digest_into_mp.py` |
| 4 | **溯源**：为每句浓缩要点在原文做字符串定位 | 切片锚点（点要点高亮原文，双向联动） | `locateQuote` / `buildRawSegs` |
| 5 | **落库**：合并入池 + 同源导出 | `miniprogram/data/notices.js` ↔ `web/zhishi-data.js` | `export_mp_data_to_web.py` |
| 6 | **匹配**：事件属性 × 用户画像（身份/年级/学院/订阅） | 命中事件列表 | `store.matchNotices` / `push.buildPush` |
| 7 | **打分**：按可解释理由权重求和排序 | 带理由与分数的推送卡片 | `push.js`（`MAX_RAW=150` 归一化） |
| 8 | **提醒**：算剩余天数 → 应用内卡片 + **微信订阅消息** + **提醒时间** | 推送卡片 / 送达回执 / 提醒计划 | `wxnotify.js` / `reachlist.js` |

> **工作流可视化**：`web/index.html`（四阶段点亮）、`web/pipeline.html`（全链路）、`web/understand.html`（抽取演示）。
>
> **可复跑性**：整条链路一步一脚本，`node tools/checks/run_all.js` 一键回归（20 脚本 / 502 项断言）。

## 三、提示词与关键配置说明

> 本章对应技术评分点项中的「**提示词编写**」。本作品的理解层有两套实现，
> **对外契约完全一致**（同一 `understandNotice(notice)` 接口，页面零改动）：
> - **规则版（当前已跑通）**：零成本、可离线、结果稳定可复现；
> - **LLM 版（云服务就绪即切换）**：提示词见下方，接口已实装于 `miniprogram/utils/cloud.js`。

### （一）系统角色提示词（System Prompt）

**LLM 版实际使用的 System Prompt（原文 · 见 `utils/cloud.js`）：**

```
你是校园通知结构化助手。只从给定原文中抽取信息，绝不编造。
抽不到的字段一律填 null。严格输出 JSON，不要任何额外文字。
```

**User Prompt 模板（含 JSON Schema 约束）：**

```
请从下面这条校园通知原文中抽取结构化字段，输出 JSON：
{"who":"适用人群","what":"要做什么","where":"在哪办",
 "deadline":"截止时间(YYYY-MM-DD，没有则null)",
 "materials":"所需材料","source_quote":"支撑结论的原文片段"}

通知标题：{title}
通知原文：
{raw}
```

**调用配置**：`temperature: 0.2`（低温度，减少发挥）· `response_format: {type:'json_object'}`
· `stream: true`（流式拼接，必须 system 在前）。

**规则版的等价约束**（不依赖模型，用代码把同一条原则钉死）：
- 受众判定走**有序规则表**（学生向优先于教职工向，见 21.2 节），判不出就**如实退回"未点名"**；
- 截止日期用正则归一化为 `YYYY-MM-DD`，抽不到则为 `null`；
- 浓缩要点每句必须挂**原文引文**，定位失败回退段落级高亮——**绝不编造**。

### （二）任务规划与决策配置

- **意图识别**：本作品主链路为**任务驱动**（采集/理解/匹配分离），无开放域意图解析；
  但保留了**「问答」13 问的受控意图路由**——用户用自然语言问，系统映射到固定问题 id（`today`/`week`/`first`/`miss`…），
  **每个 id 的答案由真实字段算出**，而非自由生成（避免幻觉）。
- **任务编排**：采集 → 过闸 → 理解 → 溯源 → 落库 → 匹配 → 打分 → 提醒，**链式固定流程**，见第二章（二）。
- **决策点**：
  ① 入库两道闸门（时效 + 价值）；
  ② 推送的**打扰阈值**——只有"三天内截止"才允许打扰，其余静默进流；
  ③ 触达**规划规则**——承接 22.4 节三条硬规则。

### （五）多轮对话与记忆配置

（`wx.setStorageSync` 本地存储）+ **推送留痕**（`zhishi_push_state`，用于算 `isNew`），

### （六）提示词及关键配置优化

| 发现的问题 | 对应改进 |
|---|---|
| 模型输出夹带解释文字，JSON 解析失败 | 强化 System Prompt 约束 + `response_format: json_object` + 解析失败自动重试 |

| **受众判过头**：把"本科教学检查"当成"只给本科生看"，导致研究生漏推 | 剔除组合词后再判受众；年级词表从单一来源派生（见第四章可靠性工程） |
| **受众判不足**：图书馆活动/校园选拔赛被打成"未点名" | 有序补三条识别规则（21 节），未点名由 22 条降至 11 条 |
| 模型对"是否与学生有关"易过度发挥 | 规则版用双正则拦截非学生事项；LLM 版要求 `who` 字段抽不到即 null |

## 四、核心实现与自主贡献说明

### （一）核心功能实现

**1. 结构化五要素抽取**
以 JSON Schema 约束 LLM 输出，字段：`event_type` / `target_audience` / `deadline` /
`required_materials` / `apply_entry` / `confidence`。

**2. 原文定位算法（自主实现，核心）**
- 拿到每句浓缩要点的 `quote`；
- 在原文中做**字符串定位**，取得真实起始下标；
- 按下标把原文**切成片段数组**，每段标记「是否被引用」「对应第几个要点」；
- 渲染时按片段数组输出，实现**双向联动高亮**。
- **换一条引文，高亮位置自动跟着变**——证明是真定位，不是写死的装饰。

**3. 匹配层**
事件属性 × 用户画像（年级/学院/关注类别）做规则化筛选，结果实时可变。

**AI 推荐层（构建期模型 + 规则保底 + 双实时通道）**：理解层产出结构化字段后，再按用户画像调用大模型做「通知 × 画像」相关性判断，逐条输出相关性分、推荐理由与原文依据；构建期真调 `auto` 模型 **22/22 成功**（提示词 v1.0.0，56 秒），结果注入实用版产物，页面标注「构建期预计算 · 非实时调用」。实时形态有两条：本机 `POST /api/recommend`（自备 Key / WorkBuddy SDK）与在线版免密钥云大模型；服务不可达自动降级为规则算法。在线版另把画像与运行留痕写入云数据库（`zs_profile` / `zs_ai_trace`），浏览器实测 `ok_count=3/3`。规则加权始终保留为降级基线与可解释对照，每条模型推荐附「规则分对照」，**不把规则结果冒充 AI**。演示版刻意不接入，保持纯离线保险形态。举证见 `docs/AI推荐层_接入与验证.md` 与 `docs/在线真后端_使用说明.md`。

**持续迭代与开源借鉴（自主实现）**：答辩前浏览 GitHub 同类项目（Laya / ClawFeed / RSSBox / LiGHT / Augur），只借机制、不照搬业务，落地四项：日历导出 `.ics`、汇总 3/7/30 天时间窗、数据自查页 AI 运行留痕面板、智能体服务对外暴露安全警告。借鉴清单与不采纳理由见 `docs/GitHub借鉴与优化说明.md`，功能成熟度见 `docs/功能成熟度.md`。全部改动后 27 个守卫脚本仍全通过。

**4. 「问答」自问自答引擎（自主实现）**
不止"推给你看"，还把学生**脑子里真会冒出的疑问**做成可计算的问答——13 个问题分六组：

| 组 | 学生原话 | 答案从哪来 |
|---|---|---|
| 📅 今天 / 这周 | 今天有什么非要办的？ / 这周还剩几件事？ / 哪天我可以空出来？ | `countdown` 字段逐条筛 |
| 🎯 先办哪个 | 要是只办一件，该办哪个？ / 给我一张今日待办清单 | 推送分排序取 Top |
| 🔍 我漏了什么 | 我是不是漏了什么？ / 有没有已经过期的？ | 本地留痕比对（`isNew`） |
| 🎫 是不是给我的 | 哪些是全校都能报的？ / 哪些点名了我们学院？ / 哪些有硬门槛？ | 机会类标签白名单 + 受众文本 + 画像学院 |
| 📦 要准备什么 | 我要准备哪些材料？ | `materials` 字段拆开汇总 |
| 🛡 数据可靠吗 | 哪几条必须去官网原文看？ / 数据可靠吗？会不会骗我？ | `real` + `url` + 自查报告 |

**每一条答案都遵守三条铁律，且被机器守住：**
- **① 答案必须由真实字段算出**——不凭空生成，不对数据"发挥"；
- **② 必须附「依据」一行说明算法**——例如"统计口径：倒计时 = 0 的条目，共 1 条"，学生能逐条核对；
- **③ 算不出来就如实说"算不出来"**——数据不足时不编结论，异常时降级为"这条问题暂时算不出来（数据读取异常）"。

> **踩过的坑（真实修复）**：「哪些是全校都能报的？」最初只按受众文本匹配「全校」，
> 结果把「全校第八周专业课考试安排」也当成"可报的机会"列出来——学生看到会莫名其妙：
> 考试安排不是我能报的名。修复方式是加一层**机会类标签白名单**
> （竞赛 / 奖助学金 / 讲座培训 / 图书资源 / 转专业 / 选课），只有"要你去报名/参加"的类目才算机会。

**5. 日历（同一份数据的另一个视角）**
把有截止的通知落到**月历格子**上，回答"**具体哪天忙、哪天能空**"：
- 周一为一周起点；忙碌日按紧急度着色（今天/三天内/一周内/本月内四档）+ 圆点标记 + 多事计数；
- 默认选中今天，支持翻月、回到今天、点日期看当天明细、展开本月全部待办；
- 一句话总结（"这个月有 6 件要办，分布在 5 天"）全部由数据派生。

> **设计原则**：日历与日程**同一批数据，不是两套事实**。
> 日程回答"这周我还有几件事"，日历回答"具体哪天忙"——同一数据两种切法，结论必然自洽。

**6. 可靠性工程（本轮加固）**
- **倒计时实时刷新**：打包数据的 `countdown` 是编制时刻的定值，日子在前行。
  若直接展示，第二天打开就会看到过期数字——"今天截止"的条目会顶成"还剩 1 天"，
  该今天办的事被排到明天，**这是会误事的真 bug**。修复：所有数据入口统一过一层
  `refreshCountdowns`，按 `deadline` 与"今天"现算，保证倒计时永远是活的、与截止日恒自洽。
- **边界加固**：`splitMaterials(null/undefined)` 曾会崩（整条问答链断掉）；
  月份入参越界（0/13/-1）会算出不存在的月份；`shiftMonth` 大 delta 曾用 while 循环。
  全部修复，并写进回归测试。
- **身份受众匹配的漏推防线**：`matchAudience` 早期用 `/本科/` 直接判定受众，
  于是「**本科教学检查通知**」「本科教育教学审核评估」「本科毕业论文（设计）工作会议」
  这类**本科教学环节的工作安排**被误当成"只给本科生看"，导致研究生被自己的推送系统
  **漏推**。修复：先剔除「本科教学/教育/培养/毕业/论文/工作…」等组合词，再判是否真的在限定受众；
  同时年级词表从 `GRADES` 派生（不再手写第二份），并把 2026 级新生补进下拉。
  另清理了 `identity.js` 里从未被使用的死代码 `AUDIENCE_RULES` / `UNIVERSAL_KW`。
  两端（小程序 `push.js` + 网页 `zhishi-core.js`）同源修复。
- **「各花入各眼」学院归属过滤（本轮新增）**：一条发布在**学院自有官网**上的通知
  （如工学院官网的「第十周考试安排」），其"给谁看"由**发布单位**决定，而非正文有没有点名。
  新增 `noticeCollege`（来源→归属学院）+ `matchCollege`（学院维度可见性）：
  学院官网通知**只推给该学院学生**，其他学院排除；**校级单位**（图书馆/教务处/学工处…）
  来源仍全校可见；用户没填学院 / 明写"全校" / 来源认不出 → **放行不误杀**。
  两端来源词表（学院别名 19 条 + 校级关键词 23 条）逐项同源，由 `check_parity.py` 守卫。

> 关键代码与截图：`miniprogram/utils/store.js`（`locateQuote` / `refreshCountdowns`）、
> `miniprogram/utils/ask.js`（问答引擎 + 日历）、`web/zhishi-core.js`（同源副本）、`web/digest.html`。

**7. 真·触达：微信订阅消息闭环（自主实现）**

痛点最后一步是"到达"。应用内推送只在打开时生效，本层补上**微信服务通知**这条合规通道。

`miniprogram/utils/wxnotify.js` 做三件事，一件不少：

| 步骤 | 实现 | 合规要求 |
|---|---|---|
| ① 授权 | `wx.requestSubscribeMessage`（单次上限 3 个模板，超了自动分批） | **必须用户本人点**，绝不静默订阅 |
| ② 登记 | 订阅类别 + 提前量写入云端（`zhishi_profiles`） | 只登记意图，不读私域 |
| ③ 回执 | 记录送达留痕（`sends` / `lastSendAt`） | 可复核"到底推没推给我" |

**可降级设计（本项目的诚实原则）**：
- 有模板 ID → 走真机授权、真实下发；
- **无模板 ID / 无平台 API → 交互与登记照走，但页面明确标注"演示模式"**，
  **绝不冒充已通**；配置模板 ID 后自动转真，**用户无需重新操作**；
- 授权失败 / 用户拒绝 → 如实降级为"仅应用内推送"，不假装能推。

**8. 提醒时间引擎（自主实现）**

回答评审必问的那句"**你说会主动提醒我，凭什么信**"。

`miniprogram/utils/reachlist.js`（网页端同源为 `zhishi-core.js` 的 `buildReach`）把每条通知
从**发布到截止**摊在日程上，标出**哪天会找你、找你几次**：

- **三条硬规则**（与推送引擎同口径，杜绝"说一套做一套"）：
  ① 只有"与我有关"的条目才进规划；② 提醒日 = 截止日往前推提前量每一档、且不早于发布日；
  ③ 已过期的不再规划任何提醒；
- **不产生新数据**：全部由真实"发布日 + 截止日 + 用户提前量"算出 → **能推演、能逐条复核、断网可演**；
- 提前量可选：截止前 **7/3/1 天**（最稳）/ **3/1 天**（推荐）/ **仅 1 天**（最少打扰）。

## 五、知识库构建说明

> 本章对应技术评分点项中的「**知识库构建**」。
> **重要说明（诚实优先）**：本作品的知识库是**结构化通知知识库**（非向量库），
> 这是有意的架构选择——因为本作品的"智能"不靠语义相似度召回，而靠
> **字段可解释 + 引文可溯源**。下面逐条交代真实做法。

### （一）知识库数据源

| 项 | 内容 |
|---|---|
| 数据类型 | 校园**公开通知**文本（学工处 / 图书馆 / 校工会 / 保卫处 / 人事处 / 本科生院 / 工学院 / 经管学院 / 教务处 / 宣传部等） |
| 原始来源 | **9 个公网公开通知页**，任何人无需登录即可访问 |
| 实测规模 | 池内 **130 条**通知，其中 **124 条**带 `real:true` 且留存官网原文链接，覆盖 **13 类来源单位**；原始采集文件 **121 条** |
| 链接完整性 | **全部条目带可核对的官网原文链接**，点即回原文 |
| **被拦截站点** | 学工处 / 招办 / 就业 / 团委 / 农学院 / 林学院返回 **503**（校方安全设备 WAF 拦截）→ **不绕行、不硬闯**，在数据源面板如实标注"安全拦截" |
| **不包含** | 课表、成绩、学籍、一卡通等**任何个人数据** |

**注册表驱动**：数据源不写死在代码里，而是集中在 `data/sources.json`（SourceRegistry），
每个源绑定一个**可插拔适配器**（`ahau_vsb` 标准站 / `generic` 通用站 / `szsn_api` 数智安农后门），
新增源只需改注册表 + 声明适配器，**不改采集主逻辑**。

### （二）数据预处理流程（清洗 / 解析 / 去重）

| 步骤 | 做法 |
|---|---|
| **清洗** | 去 HTML 标签、去页眉页脚与导航噪声；标题脏则跑 `reclean_titles.py` 重清洗（无需重新联网） |
| **解析** | 抽取正文段落，保留小标题层级；列表页支持 `/index/tzgg/N.htm` 翻页 |
| **去重** | 按标题 + 正文哈希去重，同一通知多站点转载只保留一条 |
| **归一化** | 时间统一为 `YYYY-MM-DD`；单位名称标准化；受众值标准化 |
| **过闸** | 两道入库闸门：**时效闸门**（`FRESH_AFTER`）+ **价值过滤**（`LOW_VALUE_RE`/`NONSTUDENT_NEWS_RE`） |
| **溯源** | 为每条浓缩要点生成 `digestPoints[{text, quote}]`，`quote` 与原文逐字一致 |

### （三）向量数据库配置（取舍说明）

**本作品不使用向量数据库**，而是**结构化字段表 + 溯源引文锚点**。理由：

| 对比项 | 向量库（未采用） | 结构化知识库（采用） |
|---|---|---|
| 召回方式 | 语义相似度 | 字段精确匹配 + 标签 + 关键词 |
| 可解释性 | 黑箱（说不清为什么召回） | **每个理由都能核对**（如"命中年级 2025 级 +18"） |
| 可溯源 | 弱 | **强**（每句结论挂原文引文，可定位高亮） |
| 依赖 | 需向量库 + 嵌入模型 | 零外部依赖，可离线 |

> 这与本作品"**理由即分数、结论可溯源**"的设计立场一致：
> 我们宁愿要"**说得清**"，也不要"**看起来很智能但查不了**"。

### （四）检索策略

| 层 | 用途 | 实现 |
|---|---|---|
| **标签检索** | 按 9 类统一标签归类（转专业/学科竞赛/奖助学金/考试安排/选课/讲座培训/图书资源/学工事务/校内通知） | `tags.js`（单一事实来源，两端同源） |
| **关键词检索** | 精确命中（标题/浓缩/要点/标签/来源/原文） | `search.js`（加权：标题 10 · 命中次数 2 · 标签 6 · 摘要 5 · 要点 3 · 来源 2） |
| **自定义关键词订阅** | 用户自敲（如"正大杯"），命中即进通知列表 | `subscribe.js`（与检索同口径，避免"搜得到推不到"分裂） |
| **结构化筛选** | 身份/年级/学院/受众多维过滤 | `matchNotices` + 「各花入各眼」学院归属 |

### （五）知识上下文注入规则

理解层以**通知原文**为上下文直接处理；可选叠加**历史同类通知**做参考。
注入时**明确标注"以当前原文为准"**（模板见第三章（四）），
避免历史信息覆盖时效内容——**时效永远优先于历史**。

### （六）知识库更新机制

| 机制 | 说明 |
|---|---|
| **增量更新** | 采集层每次抓取后，新通知即时入库并过两道闸门 |
| **变更识别** | 按 URL 与正文哈希识别修改/删除，覆盖更新 |
| **批量导入** | 支持初始一次性导入历史公开通知 |
| **同源导出** | 数据一变，`export_mp_data_to_web.py` 一键同步到小程序与网页两份（`check_parity.py` 守卫一致性） |
| **理解层刷新** | `inject_digest_into_mp.py` 可整体重跑（含 `RESAMPLE_AUDIENCE` 模式重抽受众） |

### 已实现的主要功能

1. 完整四层链路跑通（采集 → 过闸 → 理解 → 溯源 → 匹配 → 打分 → 提醒）；
2. 结构化五要素抽取 + 受众判定 + 溯源引文；
3. **浓缩 + 全链路溯源双向联动**（核心差异化）；
4. 原生微信小程序（通知 / 详情溯源 / 日程 / 汇总 / 搜索 / 订阅 / 自查 / 推送设置 / 问答 / 日历 **十页**）；
5. **「问答」自问自答引擎**（13 问 6 组，答案带依据）与**日历**；
6. **真·触达闭环**：微信订阅消息（授权 / 登记 / 回执）+ **提醒时间**；
7. 数据源接入边界可视化面板；
